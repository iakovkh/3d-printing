# Облачное исполнение утверждённого процесса 3D-моделирования

Статус: согласованный дизайн, ожидает контрольного просмотра  
Дата: 28 сентября 2026  
Целевой репозиторий: `iakovkh/3d-printing`  
Среда исполнения: OpenAI-hosted Linux environment, без зависимости от домашнего компьютера

## 1. Цель

Перенести уже утверждённый процесс 3D-моделирования в GitHub и сделать его исполнимым из ChatGPT/Codex Cloud с телефона. Пользователь должен иметь возможность начать проект голосом или текстом, подтвердить ТЗ и концепт, просмотреть проверочные изображения, утвердить точные версию и ID, а затем скачать из GitHub неизменённый геометрический 3MF для импорта в Anycubic Slicer Next.

Домашний компьютер не участвует в создании модели. Он нужен только на последнем пользовательском этапе: скачать выпуск, открыть его в слайсере, назначить профиль и выполнить нарезку.

## 2. Нормативная основа

Облачный слой не заменяет и не переизобретает существующий контракт. Источниками обязательных правил остаются:

1. `AGENTS.md`;
2. `00_PROJECT_INSTRUCTIONS.md`;
3. `01_CLOUD_WORKFLOW.md`.

При реализации разрешены только изменения, необходимые для перехода от локального хранения к GitHub: описание веток, pull request, облачной среды, Git LFS и автоматических проверок. Порядок стадий, стоп-условия, статусы, правила версий, требования к QA, утверждению и неизменяемому выпуску сохраняются.

Фраза «Git пока не используется» в прежней документации становится устаревшей технической деталью. Git добавляется как транспорт и журнал изменений, но не заменяет версионные каталоги `vNNN`, SHA-256 и утверждение конкретного кандидата.

## 3. Граница первой облачной версии

Первая версия поддерживает тот же диапазон моделей, что и действующий контракт:

- точные функциональные детали;
- плоские изделия, надписи, логотипы и брелоки;
- органические и скульптурные модели;
- гибридные модели;
- многоцветные модели с отдельными телами.

В неё входят:

- перенос нормативных документов в корень GitHub-репозитория;
- шаблон каталога нового проекта;
- закреплённая Linux-конфигурация инструментов;
- маршрутизация между OpenSCAD, CadQuery и headless Blender;
- сборка геометрического 3MF;
- независимое повторное открытие кандидата;
- геометрический QA и обязательные проверочные изображения;
- проверка именования, версии, ID и SHA-256;
- выпуск утверждённого кандидата без пересборки;
- работа через ветку и pull request, доступная с телефона.

Не входят:

- автоматическая нарезка и обещание корректного профиля Anycubic Slicer Next;
- отправка задания на принтер;
- фоновый доступ к домашнему компьютеру;
- автоматическая публикация кандидата как выпуска без точного утверждения пользователя;
- массовая загрузка локальной папки `tools/` с Windows-версией Blender;
- массовая загрузка кэшей, vendored Python-пакетов, `__pycache__` и промежуточных `.blend`-экспериментов.

## 4. Репозиторий как единый источник состояния

Целевой репозиторий имеет следующую верхнеуровневую структуру:

```text
AGENTS.md
00_PROJECT_INSTRUCTIONS.md
01_CLOUD_WORKFLOW.md
README.md
.gitignore
.gitattributes
.github/
  workflows/
templates/
  project/
toolchain/
  requirements.lock
  versions.json
  scripts/
projects/
docs/
```

`projects/<project-slug>/` сохраняет действующую структуру `00_brief` — `05_release` без переименования стадий.

Git фиксирует авторство, обсуждение и историю коммитов. Каталоги `vNNN` остаются неизменяемыми: наличие истории Git не разрешает перезаписывать ранее показанную версию. Release считается действительным только при выполнении контракта и прохождении автоматических проверок.

## 5. Облачная среда

Каждая задача запускается в новой OpenAI-hosted Linux-среде из состояния выбранной ветки GitHub. Установка и проверка среды должны выполняться воспроизводимо из закреплённых файлов репозитория.

Минимальный инструментарий:

- Python с закреплёнными версиями библиотек для 3MF, сеток и QA;
- CadQuery для точной параметрической геометрии;
- OpenSCAD для плоских контуров и простых экструзий;
- Blender в headless-режиме для органической геометрии и технических рендеров;
- системные библиотеки, необходимые для безэкранного рендера;
- Git LFS для крупных канонических исходников.

Среда обязана проверять версии инструментов до моделирования. Незакреплённое обновление зависимости не должно незаметно менять геометрию или формат экспорта.

Секреты и токены не сохраняются в репозитории. Доступ к GitHub предоставляется средствами связанного облачного окружения.

## 6. Выбор моделирующей ветки

Инструмент выбирается по свойствам модели, а не пользователем:

- CadQuery — размерные детали, отверстия, посадки, корпуса и крепления;
- OpenSCAD/SVG — надписи, логотипы, брелоки и простые экструзии;
- Blender — органические и скульптурные формы;
- несколько канонических исходников и `source-manifest.json` — гибридные и многоцветные модели.

Выбор инструмента не меняет пользовательский контракт. Любая ветка должна закончиться тем же набором: кандидатный 3MF, повторное открытие, QA, изображения, версия, SHA-ID и только затем утверждённый выпуск.

## 7. Мобильный пользовательский сценарий

1. Пользователь открывает Codex в ChatGPT на телефоне и выбирает репозиторий.
2. Новая задача создаётся в отдельной ветке или worktree.
3. Агент сохраняет исходный запрос и формирует `requirements.md`.
4. Пока ТЗ не подтверждено, разрешены только документы brief; моделирование запрещено.
5. Для органической или неоднозначной декоративной модели отдельно создаётся и утверждается концепт с обязательной маркировкой.
6. После подтверждения агент строит геометрию, экспортирует новую версию кандидата, повторно открывает 3MF и выполняет QA.
7. В чате показываются proof sheet, размеры, части/цвета, предупреждения и точные версия с коротким ID.
8. Пользователь запрашивает следующую версию либо пишет точное утверждение версии и ID.
9. Утверждение сохраняется в проекте как прослеживаемая запись.
10. Отдельный release-шаг побитово копирует утверждённый кандидат в `05_release/vNNN`, сверяет SHA-256 и повторно открывает выпуск.
11. Pull request проходит автоматические проверки и после просмотра объединяется в `main`.
12. Пользователь скачивает `<name>_vNNN_geometry.3mf` из GitHub на компьютер и открывает его в Anycubic Slicer Next.

## 8. Ветки и защита публикации

Новая модель и каждая значимая итерация выполняются не напрямую в `main`. Рабочая ветка хранит brief, концепт, исходники, кандидаты и QA-материалы. Pull request является точкой просмотра изменений и доставки артефактов в основную ветку.

Автоматические проверки блокируют объединение, если:

- нарушена обязательная структура проекта;
- начато моделирование без подтверждённого ТЗ;
- кандидат перезаписал ранее существовавшую версию;
- отсутствует повторное открытие и QA;
- существует `BLOCKER`;
- изображения не содержат совпадающие модель, версию и ID;
- release создан без записи точного утверждения;
- SHA-256 кандидата и `geometry.3mf` различаются;
- папка release содержит смешанные версии.

GitHub branch protection настраивается после появления первого workflow и должна требовать успешный статус contract/QA validation перед объединением.

## 9. Бинарные файлы и размер репозитория

Готовый `geometry.3mf`, QA-отчёт и компактные PNG-превью должны оставаться удобными для просмотра и скачивания из GitHub. Крупные `.blend`, STEP/STL и иные канонические бинарные исходники отслеживаются через Git LFS.

Текущая локальная папка содержит примерно 1,3 ГиБ Windows-инструментов и 0,87 ГиБ существующих проектов, включая кэши, vendored-зависимости и многочисленные промежуточные `.blend`. Они не загружаются вслепую в первый коммит. Сначала из них выделяются нормативные документы, переносимый код, канонические исходники, кандидаты, QA и выпуски. Локальная Windows-сборка Blender исключается: облачная Linux-среда устанавливает собственную закреплённую версию.

## 10. Прослеживаемое утверждение

Утверждение должно содержать модель, версию, короткий ID, полный SHA-256, дату и исходную пользовательскую формулировку. Оно относится только к уже показанному кандидату.

Release-скрипт принимает путь к кандидату и запись утверждения, но не принимает геометрию для пересборки. Его единственная операция над 3MF — побитовое копирование в новое неизменяемое место с проверкой совпадения SHA-256.

Коммит, содержащий утверждение или release, не заменяет пользовательское подтверждение. Источником разрешения остаётся явная фраза пользователя в задаче; файл в репозитории сохраняет доказательство и связь с артефактом.

## 11. Проверка качества

Проверки делятся на четыре уровня:

1. **Contract lint** — структура, статусы, имена, последовательность стадий и отсутствие перезаписи версий.
2. **Geometry QA** — единицы, габариты, manifold, компоненты, нормали, критичные размеры, части и трансформации.
3. **Round-trip QA** — повторный импорт кандидатного 3MF и сравнение устойчивых характеристик с экспортированными телами.
4. **Release verification** — утверждение точных версии/ID, отсутствие `BLOCKER`, побитовое совпадение и повторное открытие выпуска.

Технические превью генерируются только после round-trip QA из повторно открытого кандидата. Художественный концепт хранится отдельно и не может удовлетворять требованиям к проверочным изображениям.

## 12. Обработка ошибок

- Ошибка установки среды останавливает задачу до моделирования.
- Ошибка генерации или экспорта оставляет статус `GEOMETRY_DRAFT` и не создаёт ложный кандидат.
- Ошибка повторного открытия или любой `BLOCKER` запрещает запрос утверждения и release.
- Неподтверждённый критичный размер возвращает проект в `WAITING_FOR_INPUT`.
- Невозможность надёжно проверить свойство записывается как явный `WARNING` или ограничение; результат не выдаётся за проверенный.
- Ошибка push или pull request не считается потерей модели: агент сохраняет состояние текущей задачи и повторяет только транспортный шаг, не пересобирая утверждённый 3MF.

## 13. Проверка реализации

Реализация считается готовой после двух уровней испытаний:

1. Репозиторные тесты проверяют шаблон, правила именования, запрет перезаписи, SHA-ID, запись утверждения и побитовое создание release.
2. Сквозной облачный smoke test создаёт небольшую параметрическую модель, собирает `candidate.3mf`, повторно открывает его, выпускает все обязательные изображения и намеренно останавливается перед release без пользовательского утверждения.

После отдельного тестового утверждения тот же smoke test должен создать release, доказать совпадение SHA-256 и предоставить 3MF, который можно скачать из GitHub и импортировать в Anycubic Slicer Next. Фактическое открытие в Anycubic Slicer Next выполняется пользователем и записывается как результат приёмки, а не симулируется облачным процессом.

## 14. Миграция текущего проекта

Миграция выполняется поэтапно:

1. Инициализировать Git-историю и связать её с пустым `iakovkh/3d-printing`.
2. Перенести существующий контракт и эту спецификацию.
3. Добавить `.gitignore`, Git LFS и правила исключения локальных инструментов/кэшей.
4. Добавить шаблон проекта и переносимые общие скрипты.
5. Добавить закреплённую облачную среду и CI-проверки.
6. Провести сквозной smoke test.
7. Отдельно инвентаризировать два существующих локальных проекта и перенести только их канонические, проверочные и выпускные артефакты без смешивания версий.
8. Выполнить первый push и включить защиту основной ветки.

Эта последовательность не меняет геометрию уже существующих моделей и не объявляет их выпущенными без предусмотренного контрактом утверждения.

## 15. Критерии готовности

Система готова, если:

- новый проект можно начать и вести с телефона при выключенном домашнем компьютере;
- агент автоматически читает существующий контракт из репозитория;
- моделирование физически блокируется до подтверждения ТЗ;
- рабочая ветка автоматически выбирает подходящий моделирующий инструмент;
- кандидатный 3MF проходит повторное открытие и геометрический QA;
- все обязательные изображения происходят из повторно открытого кандидата;
- версия и ID совпадают во всех артефактах;
- release невозможно создать без точного утверждения и при наличии `BLOCKER`;
- выпущенный 3MF побитово совпадает с утверждённым кандидатом;
- 3MF и превью доступны для скачивания из GitHub;
- выпуск успешно открывается пользователем в Anycubic Slicer Next.
